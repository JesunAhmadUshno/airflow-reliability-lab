# airflow-reliability-lab

**Question.** When an ML pipeline on Apache Airflow is hit by a fault
(a killed write, a partial write, a duplicate trigger, late data, a
scheduler restart, a mid-run deploy), does its sink still hold exactly
the right records, or only a green DAG, and do idempotent-sink design
patterns close the gap?

**Headline.** On a real Airflow 3.4.0 deployment, the naive design
corrupted the sink in 121 of 121 write-path fault trials, and every
failed naive kill or partial-write trial (100 of 100) still ended in a
green DAG run; the hardened design failed 0 of 121 (95 percent upper
bound 0.0582 per fault, pooled over n=50 kill and n=50 partial-write
trials).

**Field.** Systems and infrastructure, reliability. **Job family.**
Data and ML platform engineering.

**Verdict.** Functional. Pre-registered: SPEC.md and HYPOTHESES.md were
committed before any code (15d4e12, tag proposal-v1) and all four
hypotheses are scored by code in RESULTS.md. Tests pass in CI on
Python 3.11 and 3.12, `make reproduce` reruns the whole study, and the
real Airflow deployment ran all 305 trials (results/trials.jsonl).
Evaluated waits on the reliability profile: no stated RTO or RPO
targets, no alerting per fault, no runbook (REPORT.md).

Live dashboard: https://jesunahmadushno.github.io/airflow-reliability-lab/

```text
make setup && make test                                  # unit tests, DAG parse, report checks
PYTHONPATH=src .venv/bin/python -m airrel.report results RESULTS.md && git diff --exit-code RESULTS.md results/summary.json
make reproduce                                           # the full study, local Airflow
```

- Unit tests and the report check: `make test` (also runs in CI on
  Python 3.11 and 3.12, with the regeneration check above).
- Full study: `make reproduce` (builds the venv, stands up the local
  deployment, runs all 305 trials, regenerates RESULTS.md; about
  25 minutes on 4 cores, zero cost, local only).

## Problem

Airflow executes tasks at least once. A task can be killed after it
wrote half its rows, retried, triggered twice for the same data
interval, or re-run after late data arrives. In every one of those cases
the DAG can report success while the sink holds duplicate or stale
records. DAG status is the wrong thing to measure. The sink is the right
thing to measure.

## Purpose

Measure, on a real Airflow 3.4.0 deployment, which injected faults
corrupt the sink of five ML pipeline types, and whether three design
patterns remove the corruption: idempotent sinks with upsert on
deterministic keys, one transaction per write task, and fixed-partition
reads and writes.

## Findings

All four pre-registered hypotheses were supported (HYPOTHESES.md,
verdicts computed by code in RESULTS.md).

- RQ1: the naive append design failed every kill-mid-write,
  partial-write, duplicate-trigger, and late-data trial (failure rate 1.0 in 121 of 121
  trials). A scheduler restart corrupted neither arm. A mid-run deploy
  corrupted neither arm when the DAGs shipped in a versioned Git bundle.
- RQ2: the hardened design failed zero of its 133 fault trials. Pooled
  over the 50 kill and 50 partial-write trials, the 95 percent upper
  bound on the hardened failure rate is 0.0582 per fault.
- RQ3: every Git-bundle run executed under exactly one code version
  (four runs held version 1 across a mid-run deploy; two runs were
  serialized after the deploy and held version 2). The unversioned local
  bundle mixed versions 1 and 2 inside a single control run.
- RQ4: hardened recovery from a write fault costs exactly one extra task
  execution (100 of 100 trials), median recovery about 7 seconds. Every
  failed naive write-fault trial still ended in DAG run success:
  green-but-wrong in 100 of 100 cases.

The failure mode throughout is duplication, not loss: lost records were zero in all 305 trials. The naive arm produced 4,060 duplicate records
across the kill and partial-write trials alone.

| Fault | Naive failed | Hardened failed |
|---|---|---|
| F1 kill mid-write (n=50 per arm) | 50/50 | 0/50 |
| F2 partial write, then error (n=50 per arm) | 50/50 | 0/50 |
| F3 duplicate trigger, same interval (n=15 per arm) | 15/15 | 0/15 |
| F6 late-arriving data, re-run (n=6 per arm) | 6/6 | 0/6 |
| F4 scheduler restart mid-run (n=9 per arm) | 0/9 | 0/9 |
| F5 code deploy mid-run, Git bundle (n=3 per arm) | 0/3 | 0/3 |

Clean controls: 36 trials, zero failures in both arms. Total: 305
trials, results/trials.jsonl holds every record. RESULTS.md is generated
from those records by src/airrel/report.py and is never edited by hand.

## Architecture

- Five DAGs (ingestion, embedding, evaluation, retraining, monitoring)
  in dags_src/, deployed through a Git DAG bundle into a local Airflow
  3.4.0 deployment (LocalExecutor, SQLite metadata DB) run by harness/.
- One deterministic synthetic corpus (200 documents per partition, a
  shifted-vocabulary partition for drift, 40 late documents per
  partition), generated by src/airrel/corpus.py.
- Two arms selected per run through dag_run.conf. Naive: append inserts,
  commit per batch, latest-data reads, wall-clock keys. Hardened: one
  transaction per write task, DELETE plus INSERT upsert on deterministic
  keys, fixed-partition reads and writes, artifacts by temp path plus
  atomic rename.
- The checker (src/airrel/checker.py) re-derives the expected sink
  content from the corpus spec, independently of the pipeline code, and
  counts duplicates, losses, and content mismatches after every trial.
- Faults are injected from inside the write task (kill at 50 percent of
  rows, partial write then error) or by the harness (duplicate trigger,
  scheduler process kill and restart, mid-run bundle deploy, late-data
  re-run).

## Live dashboard

https://jesunahmadushno.github.io/airflow-reliability-lab/ is built from
site/ by .github/workflows/pages.yml. Every number on it is read at build
time from results/, the Markdown files and the Python sources. It replays
the recorded trials (labelled recorded), runs a model of the two write
paths in the browser (labelled model), and ports stats.py to a live
bounds calculator. `cd site && npm ci && npm run build` runs a
known-answer check (site/src/stats.check.mjs) before the build: the
JavaScript bounds must match summary.json and RESULTS.md, and the
write-path model must reproduce the recorded duplicates of every trial
it covers.

## Limitations

- Sinks and the metadata DB are SQLite. The patterns are database
  patterns, but Postgres behaviour (locking, isolation) is not measured.
- The embedder is a deterministic stand-in. Outcome equality is exact
  match, not the tolerance a learned model would need.
- F4 covers three of five pipelines and F6 two of five (DECISIONS.md
  D6). F5 covers ingestion only, three trials per arm.
- Trial counts bound the claim, they do not prove perfection: the
  hardened write-fault failure rate is bounded at 5.8 percent (95
  percent, pooled n=50 per fault), and the F4, F5, and F6 bounds are
  wider.
- One machine, LocalExecutor, one Airflow configuration. No distributed
  executor, no managed Airflow, no host reboot, no metadata DB failure.

Full threats to validity and the open gaps are in REPORT.md.
