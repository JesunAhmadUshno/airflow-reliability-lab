# AIR-REL Study Specification

Study: Effectively-once ML pipelines on an at-least-once orchestrator (Apache Airflow 3.x).
Date pre-registered: 2026-11-06. This file and HYPOTHESES.md are committed before any experiment code.
Programme: AI Platform Research Programme, Phase 3 (charter) and Gap-Closure Programme Batch 3.
Research base: Claude Verdict Pack 03 (Apache Airflow for ML Workflows), verified and corrected in RESEARCH.md.

## 1. Research object

The research object is external-effect correctness, not DAG success. Airflow 3.x executes tasks
at-least-once: a failed task is retried, so a task can run more than once. The study tests whether
ML pipelines still reach effectively-once outcomes in their sinks (zero duplicate records, zero
lost records) under injected faults, and which design patterns make the difference.

Research questions (from the research pack):

- RQ1. Which fault types break a naive ML DAG, and how often?
- RQ2. Do idempotent sinks, deterministic keys and partition overwrite remove those failures?
- RQ3. Does DAG version pinning stop a mid-run code deploy from mixing two pipeline versions in one run?
- RQ4. What is the recovery time and re-run cost per fault type?

## 2. System under test

- Orchestrator: Apache Airflow 3.x from official PyPI, exact version pinned in requirements-lock.txt
  and recorded in results/environment.json.
- Executor: LocalExecutor. Metadata DB: SQLite (local file). One scheduler, one DAG processor,
  one API server, all local processes started by the harness.
- DAG loading: one Git DAG bundle built by the harness from the committed templates in dags_src/.
  Git bundles support versioning; each DAG run records the Git commit it was created with
  (official Airflow documentation, Dag Bundles page; see RESEARCH.md).
- Sinks: one SQLite database file per trial. Artifact store: a local directory per trial.
- No cloud, no paid service, no external network calls during trials.

## 3. Corpus

Deterministic synthetic corpus, generated by a seeded generator (src/airrel/corpus.py):

- Base partitions: 2026-01-01, 2026-01-02, 2026-01-03, 200 documents each.
- Shifted partition: 2026-01-09, 200 documents drawn from a disjoint vocabulary (monitoring control).
- Late data: 40 extra documents for a partition, generated with a separate seed stream and appended
  to that partition's source file only when fault F6 is armed.
- Each document: doc_id (partition-scoped, for example p20260102-d0007), plain text body of 40 to 80
  tokens from a fixed 400-token vocabulary, and a content hash (SHA-256 of the body).
- The trial partition is 2026-01-02 unless a trial states otherwise.

## 4. Embedding model (deterministic stand-in)

The research object is effect correctness, not embedding quality, so the embedding step uses a
deterministic hash embedder (model_version "hash-embed-v1"):

- Tokenize: lowercase alphanumeric tokens.
- For each token, take SHA-256 of the token; use bytes 0 to 3 as a bucket index into 32 dimensions
  and byte 4 parity as a sign; add the signed count.
- L2-normalize, round each component to 6 decimals.
- vec_hash: SHA-256 of the comma-joined rounded components.

The embedder is a written spec, not shared code: the invariant checker reimplements it
independently. Outcome equality on re-runs is exact (tolerance zero), stated in advance.

## 5. Pipelines and arms

Five pipeline types, each a DAG with two tasks (prepare, then write). Every DAG takes an arm
parameter (dag_run.conf "arm": "naive" or "hardened") and a partition parameter.

| Pipeline | Sink table | Natural key (checker grouping) | Effect |
|---|---|---|---|
| ingestion | documents | (partition, doc_id) | one row per source document |
| embedding | embeddings | (partition, doc_id, model_version) | one vector row per document |
| evaluation | eval_runs | (partition, model_version) | exactly one eval row per partition |
| retraining | model_registry | (partition, model_name) | exactly one registry row, plus one artifact file |
| monitoring | drift_reports | (partition, reference_partition) | exactly one drift report row |

Arm definitions (the only difference between arms is the write pattern):

- NAIVE: append-only INSERT for every row; commit after every batch of 25 rows; reads use the
  latest available data (embedding reads all documents currently in the sink, all partitions);
  run-scoped tables (eval, registry, drift) keyed by a wall-clock timestamp string, so each
  execution creates a new row; retraining artifact written directly to its final path.
- HARDENED: one transaction per write task (all rows or none); upsert on the deterministic
  natural key (INSERT OR REPLACE); reads and writes scoped to the fixed run partition;
  run-scoped tables keyed by a deterministic key built from partition and version;
  retraining artifact written to a temporary path, then atomically renamed (os.replace).

Both arms run the same task code paths except for the write and read functions in
src/airrel/writes.py. Retries: every write task has retries = 1 and retry_delay = 5 seconds.

Monitoring outcome: the drift statistic is the distance between the mean embedding of the run
partition and the mean embedding of the reference partition (2026-01-01). The drift flag is
statistic > 0.5, a threshold fixed here in advance. Clean controls run monitoring on an
in-distribution partition (expected flag false) and on the shifted partition (expected true).

## 6. Fault matrix (pre-registered)

Faults are armed per dag run through dag_run.conf, except F4 and F5, which the harness drives.

- F1 kill_mid_write: the write task process kills itself with SIGKILL after processing 50 percent
  of its rows (naive: after committing the batches below 50 percent; hardened: after executing
  50 percent of its inserts inside the open transaction). Airflow retries the task.
- F2 partial_write_error: the write task raises a RuntimeError after processing 50 percent of
  its rows, with the same commit behaviour as F1. Airflow retries the task.
- F3 duplicate_trigger: the harness triggers two dag runs for the same partition, back to back,
  with no fault inside the tasks. Both runs are expected to succeed.
- F4 scheduler_restart: the write task runs in slow mode (about 16 seconds). The harness kills
  the scheduler process at about 40 percent of the run, waits 5 seconds, and restarts it.
  Scope: ingestion, embedding, retraining. No other runs are active during F4 trials.
- F5 code_deploy_mid_run: the harness commits a new DAG code version (CODE_VERSION marker and
  marker text change) to the bundle repository while an ingestion run is between its two tasks
  (the second task waits on a gate file). Each task records its CODE_VERSION into the sink
  table run_markers. Scope: ingestion, both arms. Exploratory control: one run under a local
  (unversioned) bundle, reported separately, not part of the H3 verdict.
- F6 late_data_rerun: a clean run completes for the trial partition; then the 40 late documents
  are appended to the source; then the harness triggers a re-run for the same partition.
  Scope: ingestion, embedding (late data enters at ingestion and propagates to embedding;
  same-interval re-runs of downstream pipelines are F3).

Trial counts (n per cell):

- Clean controls: n = 3 per pipeline per arm (30 runs), plus monitoring shifted controls n = 3 per arm.
- F1: n = 10 per pipeline per arm (100 runs). F2: n = 10 per pipeline per arm (100 runs).
- F3: n = 3 per pipeline per arm (30 runs).
- F4: n = 3 per pipeline per arm over 3 pipelines (18 runs).
- F5: n = 3 per arm (6 runs), plus 1 exploratory local-bundle control.
- F6: n = 3 per pipeline per arm over 2 pipelines (12 runs).

Runtime adaptation rule (pre-registered): if the median wall time of a smoke trial exceeds
25 seconds, n for F1 and F2 drops to 6 per cell, and the change is recorded in DECISIONS.md
before the matrix starts. No other count may change after the matrix starts.

## 7. Invariants and metrics

After every trial, an independent checker (src/airrel/checker.py) reads the trial sink and the
source corpus, and computes, per pipeline table:

- duplicates: rows in the sink minus distinct natural keys (surplus rows inside a natural-key
  group count as duplicates).
- losses: expected natural keys with no row in the sink.
- content_mismatches: rows whose stored content hash or vector hash differs from the value the
  checker computes from the source corpus.
- version_mix (F5 only): number of distinct CODE_VERSION values recorded for one dag run.

A trial fails if duplicates > 0 or losses > 0 or content_mismatches > 0 (or version_mix > 1
for F5). The checker never imports DAG or write code; it shares only the corpus on disk.

Recovery and cost (per trial, from the Airflow metadata DB and harness timestamps):

- recovery_seconds: for F1, F2, F4, time from fault injection to the dag run reaching a
  terminal state; for F3, the duration of the second run; for F6, the duration of the re-run;
  not defined for F5.
- extra_task_executions: total task-instance tries in the trial minus the task count of one
  clean run of the same pipeline.
- green_but_wrong: the dag run (or final run, for F3 and F6) ended in state success while the
  trial failed its invariants.

Uncertainty: every zero-failure cell is reported with the exact one-sided Clopper-Pearson
95 percent upper bound for its n, and pooled per fault across pipelines for each arm (the
write pattern is one shared implementation per arm, so pooling is the primary analysis for
RQ2; per-cell results are secondary). Failure rates for failing cells are reported as counts
with the same bound method.

## 8. Reproduction

One command reruns the whole study on a fresh checkout (see README.md): it creates a virtual
environment, installs requirements-lock.txt, builds the bundle, starts Airflow, runs the
matrix, checks the invariants, and regenerates results/ and RESULTS.md. Trial-level raw
records are written to results/trials.jsonl by the harness; RESULTS.md is generated from
that file by src/airrel/report.py and is never hand-typed.

## 9. Scope limits stated in advance

- One machine, LocalExecutor, SQLite metadata DB and sinks. Results do not transfer to
  distributed executors or production scale without new evidence.
- The embedder is a deterministic stand-in. Nothing here measures embedding quality.
- Side effects outside the sink (emails, alerts, paid APIs) are not measured. The registry
  artifact file is the only file side effect, and it is checked.
- The monitoring drift method is a single mean-vector distance with a fixed threshold.
  A detection-method comparison is out of scope (Deep pass).
